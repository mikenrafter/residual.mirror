Pinned behavior for the base-force toggle-back question: toggling a component OFF that restores a base force's `updatedForces[id].components` to exactly match the base force's original `components` list **prunes the `components` key out of the update entry** (or deletes the whole entry if `components` was the only key set) rather than leaving a no-op array sitting in state. This keeps state minimal and avoids a spurious update line downstream in `model.ts`'s `toCommandLines`. If other fields (e.g. `description`) are already set on that update entry, only `components` is pruned — the entry itself survives. This is documented as a code comment at the top of `actions.ts` and pinned by three tests: "toggling a component OFF for a base force that restores the original list prunes the updatedForces entry entirely", "toggling OFF a restoring component preserves other already-set fields on the update entry, pruning only components", and the seed/add-on-first-toggle and remove-from-original-list cases.

`addForceRow` returns `{ state, tempId }` (not just `state`) so the DOM layer can open the new row in edit mode immediately; tempIds are generated as `"NEW-&lt;n&gt;"` with `n` derived from the max existing `NEW-&lt;number&gt;` tempId + 1 (collision-proof even after a hypothetical future row-removal action).
