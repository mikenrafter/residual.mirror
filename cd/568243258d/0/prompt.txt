## Schema / type rules to encode in types + tests
- `Force` is an enum or tagged struct: Purpose | Stressor; fields naive_change + outcomes; NO traits; NO component lists.
- `Residue` = force id + component id (+ status/notes).
- `Attractor` has positive_state + negative_state; no valence field in the new type (legacy CSV may still have it until migration).
- Verification one-way tags: tagged-in-code ⇒ must be in metadata; metadata-only is OK.
- Personas: Verification rejects walks/sessions when fewer than 2 personas (until alpha/beta exist).
- Sessions: lockfile + change-detection hash; on drift require `--force` or show diff flag.
- Migration: naive → v3 function exists and is tested (even if naive is current CSV + old config.toml).
- Storage.Config parses v3 TOML.
- Structure can filter/sort/group records by attractor (default), not only creation order.
- CLI: grep/test that process/fluency guidance is NOT in a single shared preamble module; it is per-subcommand help/about.
